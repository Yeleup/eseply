# Деплой и боевой сервер

Production — один сервер `esepteu` и на нём один Docker Compose стек из `docker-compose.yml` без
`docker-compose.override.yml`: приложение (`app`, Octane на FrankenPHP), очередь (`queue`),
планировщик (`scheduler`), MariaDB (`db`) и Redis (`redis`). Makefile выбирает этот стек сам, по
`APP_ENV=production` в `.env` сервера. Код лежит внутри образа, поэтому `git pull` без пересборки
ничего не меняет: новый код выкладывает `make deploy`.

## Доступ к серверу

Общая часть — команды `server-kit`, `server-status`, `harden` и общее правило «Боевые серверы» для
агентов — в репозитории [server-kit](https://github.com/Yeleup/server-kit) (приватный: команды и что
они делают — README, подключение сервера — `docs/new-server.md`, переезд — `docs/migration.md`).
Здесь — то, что относится к esepteu.

- **Кто заходит.** Владелец. Агенты (Claude, Codex) — по общему правилу «Боевые серверы», которое им
  ставит `server-kit install`; координаторы очереди, исполнители, ревьюеры и задачи по расписанию на
  сервер не ходят. Правило проекта — [.ai/guidelines/prod-server.md](../.ai/guidelines/prod-server.md)
  (оно же в `CLAUDE.md`, `AGENTS.md` и `GEMINI.md`).
- **Как.** Алиас `esepteu-prod`, пользователь `developer`, проект в `~/eseply` (клон
  `git@github.com:Yeleup/eseply.git`). Адрес сервера есть только в `~/.ssh/config` владельца и в
  настройках server-kit, в репозиторий его не пишут. Технического замка для агентов нет — держит
  правило.
- **Деплой агентом.** `server-kit job esepteu deploy -- 'cd ~/eseply && make deploy'`, затем
  `server-kit job-wait esepteu <задание>` (имя задания печатает `job`). Первый деплой с блокировкой —
  иначе, [см. ниже](#первый-деплой-с-блокировкой). Об успехе агент говорит только после кода
  завершения 0 и проверки, что приложение отвечает. Отката нет: команды отката не существует.
  Состояние — `ssh esepteu-prod 'cd ~/eseply && make deploy-status'`, нагрузка — `server-status esepteu`,
  ошибки приложения — `server-kit logs esepteu --errors`. Владелец может деплоить и сам:
  `cd ~/eseply && make deploy`. Если в это время уже идёт деплой агента (или наоборот), вторая
  команда сразу отказывает ([«Одна команда за раз»](#одна-команда-за-раз)).
- **Лог приложения.** Каталог `storage` проекта смонтирован в контейнеры, и Laravel пишет лог в
  `~/eseply/storage/logs/` (`laravel.log` или ежедневные `laravel-<дата>.log` — по `LOG_CHANNEL` и
  `LOG_STACK` в `.env`). Этот путь `server-kit logs` берёт из настройки сервера в server-kit
  (`app_log=eseply/storage/logs/laravel*.log`, см. `docs/new-server.md`).
- **Соседи по серверу.** Сервер общий: рядом работает one-market (свой compose-проект, приложение на
  порту 8500), там же лежат копии sala и satu-plus. Копия sala остановлена не целиком: её контейнеры
  `db` и `redis` запущены (порт её базы 8801 — тот, что открыт в ufw); satu-plus остановлена. Цели
  Makefile esepteu меняют только свой compose-проект — на сервере он называется `eseply`
  (`DOCKER_PROJECT_NAME` в `.env` сервера, контейнеры `eseply-app-1`, `eseply-queue-1` и т. д.), его
  приложение — на порту 8600 (`APP_PORT` в `.env` сервера). Перезапуск Docker и перезагрузка сервера
  задевают и one-market.
- **Что на сервере открыто и закрыто.** Сервер подготовлен `harden esepteu --apply` (24.11.2026):
  вход developer только ключом, root по паролю остаётся, sudo без пароля, fail2ban, автообновления
  безопасности, файрвол ufw с портами 22, 80, 443 и портами баз 8801 и 3366 (открытые порты `db` —
  решение владельца для всех серверов, README server-kit, «Решения владельца»). Сайт открывают по
  домену через веб-сервер на 80/443, он проксирует домен на `127.0.0.1:8600`. `docker-compose.yml`
  публикует порт приложения как `${APP_PORT:-8500}:8000`, а в `.env` сервера
  `APP_PORT=127.0.0.1:8600`: порт приложения опубликован только на loopback сервера, и напрямую, без
  веб-сервера, приложение не открывается ни снаружи, ни из соседних сетей Docker. Порт MariaDB
  (`${FORWARD_DB_PORT:-3350}:3306`) `docker-compose.yml` публикует без адреса, то есть на всех
  адресах сервера. `TRUSTED_PROXIES` в `.env` сервера задан адресом шлюза сети стека — с него
  веб-сервер приходит в приложение. Порт 8500, который подготовка закрыла в ufw по IPv6
  (`--allow-close 8500/tcp`), — порт one-market, а не esepteu. Текущее состояние показывает
  `harden esepteu --check`.
- **Проверка изоляции для Kaspi** — пункты 3–8 и 12 чек-листа включения
  ([docs/modules/kaspi-online.md](modules/kaspi-online.md), «Чек-лист включения»), 24.11.2026,
  Docker 28.1.1:
  - пункт 3: `APP_PORT=127.0.0.1:8600`, веб-сервер ходит на `127.0.0.1:8600`, после `make deploy`
    сайт открывается;
  - пункт 4: снаружи по IPv4 порт 8600 недоступен; по IPv6 на 8600 никто не слушает и правил NAT для
    него нет, а внешнюю проверку по IPv6 сделать было не с чего;
  - пункт 5: из временной сети и из сетей всех остальных проектов Docker на сервере запросы к шлюзам,
    к публичному адресу сервера на 8600 и к контейнеру приложения на 8000 не проходят, а выход в
    интернет и к веб-серверу хоста из тех же сетей есть (контроль); `/etc/docker/daemon.json` нет, у
    сети стека нет опций, у демона нет переменных окружения, контейнеров с сетью хоста нет;
  - пункт 6: заголовки веб-сервера в порядке;
  - пункт 7: `TRUSTED_PROXIES` — точный адрес шлюза сети стека, его подтвердила строка лога
    `not_configured` до изменения;
  - пункт 8: запросы через домен, в том числе с подменой `X-Forwarded-For`, получают `5` и пишутся в
    лог с причиной `not_kaspi` и адресом шлюза стека;
  - пункт 12: очередь и планировщик работают;
  - остальных пунктов чек-листа (1–2, 9–11, 13–14) эта проверка не касалась.
- **Если ноутбук или его копия попали в чужие руки** — порядок в server-kit, `docs/new-server.md`,
  одноимённый раздел.

## Обычный деплой

```bash
cd ~/eseply && make deploy
```

Если на сервере ещё Makefile без блокировки (`make deploy-status` отвечает
`No rule to make target 'deploy-status'`), первый раз деплоят иначе — по
[«Первый деплой с блокировкой»](#первый-деплой-с-блокировкой).

Порядок:

1. Проверки: команда запущена не из git worktree, compose-проект `DOCKER_PROJECT_NAME` принадлежит
   этому каталогу.
2. Блокировка production-стека ([«Одна команда за раз»](#одна-команда-за-раз)) — до `git pull`.
3. `git pull`. Если он не удался, деплой останавливается: ничего не пересобрано.
4. Дальше шаги идут по скачанной версии Makefile: make прочитал Makefile до `git pull`, поэтому
   шаги выполняет новый make, который читает скачанный. Изменение самих шагов действует уже в том
   деплое, который его принёс.
5. `docker compose up -d --build --remove-orphans`: сборка образа, затем пересоздание контейнеров, у
   которых изменились образ или описание, — `app`, `queue`, `scheduler`. Пока пересоздаётся `app`,
   приложение недоступно: деплой идёт с коротким простоем. `db` и `redis` пересоздаются, только если
   изменилось их описание в `docker-compose.yml`. Если сборка упала, контейнеры остаются прежними.
6. `php artisan migrate --force` в контейнере `app`. Миграции идут после запуска нового кода: несколько
   секунд новый код работает со старой схемой базы. Ошибка миграции останавливает деплой — новый код
   уже запущен, `queue:restart` не выполнен.
7. `php artisan queue:restart`: воркеры очереди заканчивают текущее задание и перезапускаются.
8. Блокировка освобождается: после последнего шага, после ошибки любого шага и при обрыве команды.

Отката нет: команды отката не существует.

Если деплой оборвался (Ctrl+C, разрыв связи, ошибка шага), блокировка свободна, как только закончились
процессы команды. Повторный `make deploy` продолжает с того, что осталось: `git pull` не скачает уже
скачанное, `docker compose up` приводит контейнеры к описанию, `migrate` применяет оставшиеся
миграции.

### Первый деплой с блокировкой

Один раз — на сервере, где Makefile ещё без блокировки. Обычный `make deploy` там не годится: make
читает Makefile один раз, до `git pull`, и весь этот деплой — `git pull` и старые шаги — идёт по
старому Makefile без блокировки. А команда, запущенная во время него, уже читает скачанный Makefile,
свободно берёт блокировку и меняет стек одновременно с деплоем. Поэтому:

1. Убедиться, что на сервере не идёт другая команда стека — деплой агента, `make up` и т. п.:
   команды старого Makefile блокировку не берут и не проверяют, исключить их можно только так.
   `pgrep -ax 'make|docker|docker-compose'` ничего не показывает (сравнивает имя процесса, поэтому
   оболочка, в команде которой есть слово make, не в счёт).
2. Одной командой:
   ```bash
   cd ~/eseply && git pull && make deploy
   ```
   Агент — по просьбе владельца:
   `server-kit job esepteu deploy -- 'cd ~/eseply && git pull && make deploy'`, затем `job-wait`.
   Первый `git pull` кладёт новый Makefile и `docker/deploy/deploy.sh` и стек не меняет: код попадает в
   контейнеры только при сборке, а из каталога проекта в них смонтирован лишь `storage`. `make deploy`
   запускается после него и читает уже новый Makefile, поэтому блокировка — с первого шага, а его
   собственному `git pull` скачивать уже нечего. Команды, запущенные после первого `git pull`, тоже
   читают новый Makefile и, пока идёт деплой, отказывают.
3. `make deploy-status` отвечает и показывает `lock: free, last taken by make deploy …`.

Дальше — обычный `make deploy`.

### Команды Makefile в production

| Команда | Что делает | Блокировка |
|---|---|---|
| `make deploy` | деплой, порядок выше | берёт до `git pull`, держит до последнего шага |
| `make deploy-status` | коммит, отставание от ветки, которую приносит `git pull`, правки на сервере, блокировка, контейнеры | не берёт, работает и во время деплоя |
| `make build` | собирает образ и пересоздаёт изменившиеся контейнеры, как шаг 5 деплоя, но без `git pull`, миграций и `queue:restart` | берёт |
| `make up` | запускает стек без сборки; пересоздаёт контейнеры, у которых изменилось описание | берёт |
| `make down` | останавливает и удаляет контейнеры; тома с базой и Redis остаются | берёт |
| `make down-volumes` | то же и удаляет тома — базу и данные Redis | берёт |
| `make restart` | `make down`, затем `make up` | берёт одну на оба шага: между ними другая команда не начнётся |
| `make ps`, `make logs`, `make artisan`, `make shell`, `make dump`, `make dump-media` | смотрят на стек или работают в запущенных `app` и `db` | не берёт |
| `make import`, `make import-media` | заменяют базу и `storage/app` содержимым дампа; в production не отказывают — только по просьбе владельца, как при переезде | не берёт |
| `make db-up`, `make test` | в production отказывают | — |

### Одна команда за раз

`make deploy`, `make build`, `make up`, `make down`, `make down-volumes` и `make restart` меняют
production-стек и выполняются по одной: каждая берёт общую блокировку и держит её до конца,
`make deploy` — ещё до `git pull`. Так деплой агента через `server-kit job` и команда владельца из
своего терминала не перемешаются. Если блокировка занята, вторая команда сразу завершается с ошибкой
и ничего не делает — не ждёт и в очередь не встаёт. В ошибке — что уже идёт, его процесс и с какого
времени:

```
error: the production stack is busy: make deploy (pid 12345) since 2026-11-24 14:05:10 +0500. Nothing was done; run the command again when that one has finished
```

Команду повторяют, когда та закончится. `make deploy-status` и остальные цели блокировку не берут и
работают и во время деплоя. `make deploy-status` показывает, занята ли она и кем:

```
commit: 1a2b3c4 2026-11-24 12:00 +0500 <тема коммита>
upstream: origin/master, commits behind: 2, ahead: 0 (fetched just now)
local changes: none
lock: held by make deploy (pid 12345) since 2026-11-24 14:05:10 +0500
containers:
<docker compose ps -a>
```

Ветку, которую приносит `git pull` (`origin/master`), `make deploy-status` скачивает с GitHub в
отдельную ссылку `refs/deploy-status/upstream`: ни `origin/master`, ни `FETCH_HEAD`, ни рабочая копия
от этого не меняются, и `git pull` идущего деплоя не споткнётся о них. Если GitHub отказал или не
ответил за 20 секунд, отставание считается по последнему `git pull`, а в строке сказано почему.
`local changes` — изменённые на сервере файлы из git: с ними `git pull` может отказаться.

Блокировку держит не файл, а процессы команды: сама команда и всё, что она запустила (`git pull`,
`make`, `docker compose`). Ни один из них не меняет стек без блокировки, и она свободна, когда
закончились все. Ctrl+C, закрытый терминал и перезагрузка сервера останавливают команду целиком —
блокировка сразу свободна, снимать её руками не нужно. Если остановить только сам процесс команды
(`kill -9 <pid>`), запущенные им `git pull` или `docker compose` доработают и до своего конца держат
блокировку.

В `.deploy/lock` — строка о команде, которая взяла блокировку последней; сама она ничего не
блокирует. Отказ и `make deploy-status` показывают её, только пока процесс этой команды держит
блокировку. Иначе — процесс команды остановлен отдельно, другая команда только что взяла блокировку и
ещё не записала строку или блокировку взяли вручную через `flock` — они перечисляют процессы, которые
держат блокировку сейчас. Держатель — процесс, на дескрипторе которого ядро показывает блокировку
(`/proc/<pid>/fdinfo`), открыт ли файл на запись или на чтение; процесс, который файл только читает
(`cat`, `less`), не держатель:

```
error: the production stack is busy: the lock is held by pid 23456 (git pull); .deploy/lock names make deploy (pid 12345) since 2026-11-24 14:05:10 +0500, which no longer holds it: …
```

Если такой процесс завис, его останавливают по pid из ошибки (`kill <pid>`; агент — только по
просьбе владельца). Когда закончились все перечисленные, блокировка свободна.

Что держать в голове:

- Процессы видны только своему пользователю, поэтому `make` на сервере запускают от `developer` и не
  через `sudo`. Команду другого пользователя блокировка тоже не пропустит, но назвать её процессы
  ни отказ, ни `make deploy-status` не смогут: `make deploy-status` покажет
  `lock: held by a command whose processes are not visible to this user`. Занята ли блокировка, он
  узнаёт у ядра, не беря её: по держателям, которых видит, и по списку блокировок `/proc/locks`, где
  на сервере видна любая блокировка. Если ни то, ни другое не решает, он пишет `lock: unknown, …`, а
  не `free`: так бывает в контейнере, где ядро не показывает блокировку закончившегося `flock`, а
  процессы держателя не видны. Если `.deploy/lock` создала команда от root, команды `developer`
  отказывают с «cannot create .deploy/lock», пока файл не вернут `developer`.
- `.deploy/` нет в git (`.gitignore`) и в образе (`.dockerignore`), `git pull` его не трогает. Пока
  идёт команда, `.deploy/` не удаляют и `git clean -x` на сервере не запускают: новый файл — новая
  блокировка, и вторая команда её получила бы.
- `git pull` держит блокировку вместе со всем, что запустил: фоновое ssh-соединение, которое git
  оставил бы после себя (`ControlPersist`), держало бы её так же долго. Поэтому ssh, которым git на
  сервере ходит в GitHub (ключом id_rsa), таких соединений оставлять не должен.
- На сервере нужен `flock` (util-linux).

Локально (`APP_ENV` не `production`) и в git worktree блокировки нет: `make build`, `make up`,
`make down`, `make down-volumes` и `make restart` работают как раньше. `make deploy` берёт её всегда:
он всегда работает с production-стеком.

## Перенос на другой сервер

Общий порядок — временный ключ server-kit, перенос файлов и порядок переключения — в
`docs/migration.md` [server-kit](https://github.com/Yeleup/server-kit), подключение нового сервера —
в его `docs/new-server.md`. Здесь — шаги esepteu. Команды `server-kit` — с ноутбука владельца;
`<новый>` — имя нового сервера в server-kit, как `esepteu` у нынешнего.

Команды стека на серверах, кроме целей Makefile, выполняются в одной оболочке после двух строк:
`.env` загружен, compose-файл — тот же, что у Makefile в production (без `-f docker-compose.yml`
compose подключил бы `docker-compose.override.yml` локальной разработки):

```bash
cd ~/eseply && set -a && . ./.env && set +a
prod() { docker compose -p "$DOCKER_PROJECT_NAME" --env-file .env -f docker-compose.yml "$@"; }
```

1. **Новый сервер готов, стек не запущен.** Сервер подключён к server-kit, проект склонирован в
   `~/eseply` под `developer` ключом id_rsa владельца, без новых ключей (README server-kit, «Решения
   владельца»): `git clone git@github.com:Yeleup/eseply.git ~/eseply`. Веб-сервер перед приложением
   настроен так же, как на старом; временный ключ открыт:
   `server-kit transfer esepteu <новый> open --path /home/developer/eseply`. Стек на новом сервере не
   запускают до шага 7: воркеры очереди и планировщик не должны работать на двух серверах сразу.
2. **`.env` — целиком и тот же:** `server-kit transfer esepteu <новый> pull .env`. С другим `APP_KEY`
   перестанут читаться зашифрованные cookie и сессии: все пользователи выйдут из панели. Значения из
   `.env` в чат не выводят.
3. **Старый сервер: сайт закрыт, приложение и планировщик остановлены, очередь разобрана.** Сайт
   закрывают на веб-сервере (как и почему — общий порядок server-kit). Затем:
   ```bash
   prod stop app scheduler
   prod exec -T queue php artisan queue:monitor "${QUEUE_CONNECTION:-redis}:default"
   ```
   `queue:monitor` повторяют, пока очередь `default` не опустеет, затем `prod stop -t 90 queue`:
   воркер, который успел взять задание, дорабатывает его (у очереди нет своего `--timeout`, задание
   ограничено 60 секундами по умолчанию).
4. **Старый сервер: финальные дампы.**
   ```bash
   make dump         # база → docker/db/dump.sql.gz
   make dump-media   # storage/app → docker/db/storage.tar.gz
   ```
   Контейнеры production работают от root, и часть файлов в `storage/app` может быть закрыта для
   `developer`: тогда `make dump-media` остановится на «Permission denied», и архив собирают внутри
   контейнера приложения, без `sudo`:
   ```bash
   prod run --rm --no-deps -T --entrypoint tar app -czf - -C /var/www/html storage/app > docker/db/storage.tar.gz
   ```
   Это тот же архив, что делает `make dump-media` (пути `storage/app/…`): `make import-media` на новом
   сервере его принимает. Логи (`storage/logs`) не переносятся. Что лежит в Redis, задаёт `.env`
   (`CACHE_STORE`, `SESSION_DRIVER`, `QUEUE_CONNECTION`; без них compose подставляет Redis): кэш
   соберётся заново, сессии — это входы в панель, при очереди на Redis в нём же отложенные задания.
   Нужен ли снимок Redis, решают при переезде (общий порядок — server-kit). Файлы каталога проекта,
   кроме перечисленных в `.dockerignore`, попадают в образ при сборке: снимок под другим именем туда
   не кладут.
5. **На новый сервер:**
   `server-kit transfer esepteu <новый> pull docker/db/dump.sql.gz docker/db/storage.tar.gz`, затем
   `server-kit job-wait <новый> <задание>`.
6. **Новый сервер: только база и Redis, восстановление.**
   ```bash
   prod up -d --wait db redis
   make import         # пересоздаёт базу DB_DATABASE и заливает docker/db/dump.sql.gz
   make import-media   # storage/app из docker/db/storage.tar.gz
   ```
7. **Новый сервер: первый и единственный запуск всего стека** — `make deploy` (агент — через
   `server-kit job <новый> first-deploy -- 'cd ~/eseply && make deploy'` и `job-wait`). Воркеры и
   планировщик стартуют только здесь. Проверяют, что приложение отвечает.
8. **Переключение DNS.** TTL понижают заранее, по общему порядку server-kit. Когда домен уже ведёт на
   новый сервер, на нём выпускают сертификаты.
9. **После переезда:** `server-kit transfer esepteu <новый> revoke`; `docker/db/dump.sql.gz` и
   `docker/db/storage.tar.gz` на обоих серверах удаляют — в них данные абонентов. Каталог `.deploy/`
   не переносится: на новом сервере файл блокировки создаёт первая команда. Имя и алиас нового
   сервера владелец переводит на основное: `server-kit rename <новый> esepteu`.
