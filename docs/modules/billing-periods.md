# Модуль: Расчётные месяцы

## Терминология

Расчётный месяц в коде называется `BillingPeriod`.

Таблица расчётных месяцев называется `billing_periods`.

Статус расчётного месяца хранится в enum `BillingPeriodStatus`.

## Назначение

Модуль хранит состояние расчётного месяца внутри tenant-организации.

Расчётный месяц является самостоятельной бизнес-сущностью, а не строковым полем в начислениях, оплатах или показаниях.

## Основные поля

| Поле | Описание |
|---|---|
| Организация | Tenant-организация, поле `organization_id` |
| Начало месяца | Первый день расчётного месяца, поле `starts_on` |
| Статус | Состояние месяца, поле `status` |
| Дата открытия | Когда месяц открыт, поле `opened_at` |
| Кто открыл | Пользователь, поле `opened_by_user_id` |
| Дата запуска закрытия | Когда началось закрытие, поле `processing_started_at` |
| Дата закрытия | Когда месяц успешно закрыт, поле `closed_at` |
| Кто закрыл | Пользователь, поле `closed_by_user_id` |
| Дата ошибки | Когда закрытие завершилось ошибками, поле `failed_at` |
| Причина ошибки | Общая причина ошибки закрытия, поле `failure_message` |
| Активных абонентов | Счётчик активных абонентов на момент закрытия, поле `active_clients_count` |
| Создано начислений | Счётчик созданных начислений, поле `created_accruals_count` |
| Пропущено начислений | Счётчик пропущенных существующих начислений, поле `skipped_accruals_count` |
| Ошибок данных | Счётчик абонентов с ошибками данных, поле `failed_clients_count` |

## Отчёт ошибок закрытия

Ошибки закрытия месяца хранятся в таблице `billing_period_closure_errors`.

Каждая строка ошибки относится к одному расчётному месяцу через `billing_period_id`.

Строка ошибки хранит tenant-организацию, абонента, лицевой счёт, имя абонента, тип начисления, стабильный код ошибки, текст причины и технический контекст.

Отчёт ошибок создаётся только при переходе расчётного месяца в статус `failed`.

При повторном запуске закрытия старый отчёт ошибок очищается и заменяется новым результатом проверки.

При успешном закрытии месяца отчёт ошибок очищается.

Отчёт ошибок открывается отдельной страницей расчётного месяца, а не всплывающей панелью, поэтому объём отчёта не влияет на скорость открытия.

Страница отчёта ошибок показывает сводку месяца, разбивку количества ошибок по стабильным кодам и постраничную таблицу ошибок по абонентам.

Таблица отчёта ошибок выводит 50 строк на страницу, ищет по лицевому счёту и ФИО и фильтруется по коду ошибки и типу начисления.

Отчёт ошибок выгружается в XLSX целиком, независимо от текущей страницы, поиска и фильтров.

Стабильные коды ошибок закрытия имеют короткое описание причины, не зависящее от конкретного абонента; описание используется в разбивке по причинам.

Отчёт ошибок доступен только участнику с правом управления tenant-организацией.

## Статусы

Доступные значения `status`:

- `open` — месяц открыт для ввода оплат, показаний и корректировок;
- `processing` — выполняется закрытие месяца;
- `closed` — месяц успешно закрыт и заблокирован для изменений;
- `failed` — закрытие завершилось ошибками данных, месяц можно исправить и закрыть повторно.

## Правила

Расчётный месяц уникален внутри tenant-организации по связке `organization_id + starts_on`.

`starts_on` всегда хранит первый день месяца.

Код месяца `ГГГГММ` является отображением `starts_on`, а не отдельной колонкой в учётных таблицах.

Первый расчётный месяц tenant-организации можно открыть без предыдущей истории.

Если у tenant-организации уже есть расчётные месяцы, новый месяц должен идти сразу после последнего существующего месяца.

Новый расчётный месяц нельзя создать, пока последний существующий расчётный месяц не закрыт.

Кнопка «Новый расчётный месяц» автоматически создаёт следующий календарный месяц после последнего закрытого месяца.

Оператор не вводит код месяца вручную при открытии нового расчётного месяца.

Начисления, оплаты, показания счётчиков, корректировки сальдо и квитанции ссылаются на расчётный месяц через `billing_period_id`.

Оплаты, показания счётчиков и корректировки сальдо можно создавать, изменять и удалять только для месяцев в статусах `open` и `failed`.

Для месяца в статусе `closed` учётные данные менять нельзя.

Повторное закрытие месяца в статусе `closed` запрещено.

Повторный запуск закрытия месяца в статусе `processing` запрещён.

Месяц в статусе `failed` можно закрыть повторно после исправления данных.

Закрытие месяца состоит из двух шагов: запрос оператора занимает расчётный месяц, а расчёт выполняется фоновой задачей в очереди.

Шаг занятия расчётного месяца выполняется в транзакции и блокирует строку `billing_periods` через database row lock, чтобы два процесса не закрывали один месяц одновременно.

Занятый расчётный месяц сразу получает статус `processing`, поэтому второй запрос видит статус вместо ожидания на блокировке строки.

Начисления записываются в отдельной транзакции: либо создаются начисления по всем рассчитанным абонентам, либо ни по одному.

Расчётный месяц никогда не остаётся в статусе `processing` после технической ошибки: он переводится в статус `failed` вместе с причиной, чтобы оператор мог запустить закрытие заново.

Код расчётного месяца `ГГГГММ` всегда означает первый день своего месяца независимо от текущей календарной даты.

Если закрытие прошло без ошибок данных, месяц получает статус `closed`.

Если хотя бы по одному активному абоненту не хватает данных для расчёта, месяц получает статус `failed`.

Если месяц получил статус `failed`, оператор видит отчёт ошибок в разделе «Расчётные месяцы».

## Административная панель

Оператор управляет расчётными месяцами в разделе «Расчётные месяцы».

В разделе «Расчётные месяцы» кнопка «Новый расчётный месяц» открывает следующий месяц автоматически.

Закрытие месяца запускается кнопкой «Закрыть месяц» из раздела «Начисления».

Кнопка «Закрыть месяц» автоматически закрывает текущий расчётный месяц tenant-организации в статусе `open` или `failed`.

Кнопка «Закрыть месяц» недоступна, пока расчётный месяц находится в статусе `processing`.

Результат закрытия приходит операторам организации уведомлением в базе данных, которое оператор открывает из колокольчика уведомлений.

Для месяца с ошибками доступно действие «Отчёт ошибок»: оно открывает страницу отчёта, где отображаются лицевой счёт, ФИО, тип начисления, код ошибки, причина и технический контекст.

На странице отчёта ошибок кнопка «Скачать Excel» выгружает все строки отчёта, а кнопка «Расчётные месяцы» возвращает к списку месяцев.

В формах оплат, показаний и корректировок оператор не выбирает расчётный месяц.

Система автоматически привязывает оплаты, показания и корректировки к текущему расчётному месяцу tenant-организации в статусе `open` или `failed`.


### Принятие показаний при закрытии

На странице ошибок закрытия оператор может принять отдельный счётчик или все показания выбранного вида во всём месяце (независимо от фильтров и страницы отчёта):

- «Принять пропущенные показания»: последнее известное показание до месяца, либо начальное показание, переносится в текущий месяц с нулевым расходом. Уже введённые значения не перезаписываются. Фото и примечание визита сохраняются, дата снятия не выдумывается.
- «Принять отрицательный расход»: оператор отдельно подтверждает ошибку; текущие и предыдущие показания и отрицательный расход остаются без изменений. При закрытии такой расход уменьшает начисление и задолженность, в том числе может дать отрицательную сумму начисления.

Массовое принятие пропущенных показаний и отрицательного расхода выполняется фоновой задачей `AcceptBillingClosureMeterReadingsJob`. HTTP-запрос только ставит задачу в очередь; оператор получает уведомление с количеством принятых показаний либо уведомление об ошибке. Принятие одной строки остаётся синхронным. До завершения массового принятия повторное принятие (включая отдельную строку) и запуск закрытия этого месяца отклоняются с сообщением о необходимости дождаться операции. После завершения оператор запускает закрытие месяца вручную; чтобы увидеть обновлённый отчёт после уведомления, страницу ошибок нужно открыть заново: во время массового принятия страница не опрашивает сервер.

Задача повторно проверяет полномочия оператора, принадлежность и редактируемость месяца. Изменения показаний и удаление ошибок выполняются в одной транзакции; при ошибке обработки изменения откатываются. Резервирование освобождается при завершении, ошибке постановки в очередь или отказе задачи. Резервирование имеет защитный срок 3600 секунд; задача с лимитом 1800 секунд не начинает обработку, если оставшегося срока недостаточно. Просроченную операцию нужно запустить повторно.


Подтверждение требует согласия в диалоге и сохраняет код причины, оператора и время в показании. Изменение значений показаний, счётчика или расчётного месяца сбрасывает подтверждение; изменение примечания или фотографии его сохраняет. Контролёр подтверждать ошибки не может. Обработка доступна только для редактируемого месяца своей организации и блокирует строку месяца на время транзакции.

Массовое действие обрабатывает все активные счётчики активных абонентов с начислением по счётчику, включая следующие счётчики абонента, ещё не попавшие в отчёт. После обработки можно запустить «Закрыть месяц» прямо на странице ошибок. Закрытие повторно проверяет все данные; другие ошибки продолжают блокировать месяц.

Кнопки массового принятия показаний видны только в редактируемом месяце при наличии соответствующего кода в отчёте ошибок этого месяца. После обработки последней ошибки кнопка скрывается. Страницы начислений и расчётных месяцев автоматически обновляют таблицу и состояние каждые 5 секунд, пока у организации есть расчётный месяц в статусе `processing`; страница ошибок — пока закрывается именно просматриваемый месяц. В остальное время (`open`, `closed`, `failed`) страницы сервер не опрашивают. Интервал опроса проверяется при каждой отрисовке, поэтому опрос, заставший завершение закрытия, ещё раз отрисовывает таблицу с результатом и только после этого выключается: результат фонового закрытия виден без ручной перезагрузки.

### Эксплуатация фонового принятия показаний

На сервере нужна асинхронная очередь (`QUEUE_CONNECTION=database` или `redis`) с работающим `queue:work`. `sync` выполняет задачу в HTTP-запросе и не устраняет исходный таймаут. Worker должен иметь возможность выполнять Job до 1800 секунд; `retry_after` должен быть больше 1800 секунд (для database/redis по умолчанию в проекте — 3600). После развёртывания изменений нужно перезапустить queue workers.

Для координации HTTP-процессов и workers нужен общий cache store с атомарными блокировками, например `database` или `redis`. `array` годится только для тестов; отдельные локальные cache stores на разных серверах не обеспечивают общую блокировку. Если задача была потеряна до запуска, резервирование истечёт через 3600 секунд. Если задача ожидает дольше примерно 30 минут, её оставшегося резервирования недостаточно для безопасного выполнения: задача завершится ошибкой без обработки показаний, после чего оператор может повторить запуск.
