# Модуль: Оплаты

## Терминология

Оплата в коде называется `Payment`.

Таблица оплат называется `payments`.

## Назначение

Модуль хранит оплаты абонентов по расчётным периодам.

Оплаты используются при закрытии месяца для расчёта конечного сальдо.

`Payment` хранит только подтверждённые деньги.

Оператор вносит оплату вручную, и ручная оплата всегда наличные. Оплата способом Kaspi приходит в систему только через интеграцию по протоколу Kaspi — модуль «Kaspi онлайн» (`docs/modules/kaspi-online.md`): Kaspi-перевода, который отмечает оператор, в системе нет.

## Основные поля

| Поле | Описание |
|---|---|
| Организация | Tenant-организация, поле `organization_id` |
| Абонент | Клиент, поле `client_id` |
| Расчётный месяц | Связь с `BillingPeriod`, поле `billing_period_id` |
| Способ оплаты | Наличные / Kaspi, поле `method`: у ручной оплаты всегда наличные, Kaspi — у оплаты из интеграции и у старых ручных оплат Kaspi |
| Внешний провайдер | Провайдер интеграции, поле `external_provider`; заполнен только у оплаты, пришедшей через интеграцию |
| Внешний ID оплаты | Номер оплаты у провайдера, поле `external_payment_id`; заполнен только у оплаты, пришедшей через интеграцию |
| Принял оператор | Пользователь, который внёс ручную оплату, поле `received_by_user_id`; у оплаты из интеграции пусто |
| Сумма | Сумма оплаты, поле `amount` |
| Дата оплаты | Дата поступления оплаты, поле `paid_at` |
| Примечание | Дополнительная информация, поле `note` |

## Правила

Оплата относится к tenant-организации и абоненту.

Поддерживаемые способы оплаты: наличные и Kaspi.

Ручная оплата всегда наличные. В кассе, в карточке абонента и в разделе «Оплаты» способ оплаты не выбирается: наличные назначаются на сервере во всех путях создания, что бы ни прислал браузер, а признаки интеграции (`external_provider`, `external_payment_id`) у ручной оплаты не сохраняются.

Kaspi-перевода в системе нет: способ «Kaspi» — только у оплаты, пришедшей через интеграцию по протоколу Kaspi.

Оплата из Kaspi онлайн создаётся проводкой операции `pay`: способ `kaspi`, `external_provider = kaspi`, `external_payment_id` — номер Kaspi (`txn_id`), принявший пуст, дата оплаты — дата учёта платежа в Kaspi (`txn_date`), расчётный месяц — текущий редактируемый на момент проводки. Номер Kaspi уникален внутри организации: уникальный индекс `payments_org_provider_external_id_unique` (организация, провайдер, номер у провайдера) не даёт провести одну операцию Kaspi дважды, а в разных организациях одинаковые номера Kaspi допускаются.

При создании оплаты — в кассе, в карточке абонента, в разделе «Оплаты» и проводкой Kaspi — сначала блокируется строка абонента, поэтому одновременные оплаты одного абонента пересчитывают квитанцию по очереди и сумма в ней не теряется. Затем текущий месяц находится блокирующим чтением: начало закрытия держит строку месяца, поэтому оплата не попадает в месяц, который уже закрывается, а получает отказ «Расчётный месяц закрывается…». Квитанция пересчитывается блокирующим чтением оплат — по последним зафиксированным данным. Карточка абонента и раздел «Оплаты» сохраняют оплату штатно средствами Filament, в одной транзакции с этими блокировками.

Старые ручные оплаты способом Kaspi, внесённые до интеграции, не меняются. В таблицах оплат у них под способом подпись «внесена вручную», а у оплаты из интеграции — номер Kaspi.

Исправление оплаты способ не меняет.

Оплата из интеграции — оплата, у которой заполнен `external_provider` или `external_payment_id`. Её нельзя изменить и удалить нигде: ни в кассе, ни в карточке абонента, ни в разделе «Оплаты», ни массовым удалением. Запрет проверяет и сама модель `Payment` по сохранённым значениям, поэтому снять признаки интеграции и заодно изменить оплату одним сохранением тоже нельзя; ручную оплату нельзя выдать за оплату из интеграции. Ошибку в оплате из интеграции исправляют корректировкой сальдо.

Массовое удаление выборки, в которой есть хотя бы одна оплата из интеграции, не удаляет ни одной оплаты, а оператор видит причину.

По одному абоненту может быть несколько оплат за один расчётный месяц.

При закрытии месяца все оплаты абонента за расчётный месяц суммируются.

При создании оплаты расчётный месяц не выбирается оператором.

Система автоматически привязывает оплату к текущему расчётному месяцу tenant-организации в статусе `open` или `failed`.

Оплату можно создать, изменить или удалить только в расчётном месяце со статусом `open` или `failed`.

В закрытом расчётном месяце оплаты менять нельзя.

Если за текущий расчётный месяц у абонента уже есть квитанция, создание, изменение или удаление оплаты обновляет в ней `paid_amount` и `closing_balance`.

Оплата не создаёт квитанцию сама; квитанция создаётся при сохранении показания счётчика.

Сумма оплат за период сохраняется в начислении в поле `paid_amount`.

Конечное сальдо считается так:

`closing_balance = opening_balance + amount - paid_amount + adjustment_amount`

## Административная панель

Оплаты управляются внутри `ClientResource` как связанная таблица оплат конкретного абонента.

Отдельный раздел «Оплаты» не является основным рабочим сценарием.

Форма ручной оплаты внутри карточки абонента и в разделе «Оплаты» позволяет указать сумму, дату оплаты и примечание; способа оплаты в ней нет.

Основной поток приёма оплат вынесен на отдельную страницу «Приём оплат»: оператор находит абонента одним поиском, сверяет долг и принимает оплату, не открывая карточку. Модуль описан в `docs/modules/payment-desk.md`.

Оплату из интеграции исправить и удалить нельзя ни на странице «Приём оплат», ни в карточке абонента, ни в разделе «Оплаты»: действий у неё нет, она повторяет запись провайдера. Старую ручную оплату Kaspi исправлять и удалять можно, пока её расчётный месяц редактируем; способ при этом не меняется.

В связанной таблице оплат должны отображаться период, сумма, способ оплаты (с номером Kaspi или подписью «внесена вручную»), дата оплаты и дата создания.
