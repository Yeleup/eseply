# Дизайн: город в адресном справочнике организации

Дата: 2026-08-08

## Цель

Добавить уровень «Город» в адресный справочник tenant-организации.

Итоговая иерархия: Организация → Город → Регион → Улица.

Иерархия строгая: каждый регион принадлежит городу, каждая улица — региону.

## Схема данных

### Таблица `cities`

| Поле | Описание |
|---|---|
| `id` | Первичный ключ |
| `organization_id` | FK на `organizations`, cascade delete |
| `name` | Название города |

- Уникальность: `(organization_id, name)`.
- Без timestamps — по аналогии с `regions` и `streets`.

### Таблица `regions`

- Добавляется обязательный `city_id` (FK на `cities`, cascade delete).
- Уникальность названия региона меняется: было `(organization_id, name)`, становится `(city_id, name)`.
- `organization_id` остаётся и синхронизируется из города при сохранении региона (тот же приём, что у `Street` с регионом).

### Миграция существующих данных

- Для каждой организации, у которой есть регионы, создаётся город с названием «Город».
- Все регионы этой организации привязываются к созданному городу.
- Название города потом можно переименовать в профиле организации.

### Каскадное удаление

- Удаление города каскадно удаляет его регионы и улицы.
- У абонентов `region_id` и `street_id` при этом обнуляются (существующее поведение FK `nullOnDelete`).

## Модели

- Новая модель `City`: связи `organization` (BelongsTo), `regions` (HasMany); fillable `organization_id`, `name`; `$timestamps = false`. Фабрика `CityFactory`.
- `Region`: добавляется связь `city` (BelongsTo); в `booted()` при сохранении `organization_id` синхронизируется из города.
- `Street`: без изменений.
- `Organization`: добавляется связь `cities` (HasMany).

## Панель Filament

### Профиль организации

- Связанный справочник «Регионы» заменяется справочником «Города» (`CitiesRelationManager` вместо `RegionsRelationManager` в `EditOrganizationProfile`).
- Колонки: название, количество регионов. Действия: открыть, изменить, удалить, создать.
- Доступ — как у текущего справочника регионов: только оператор организации.

### CityResource

- Новый ресурс `CityResource` без пункта в навигации (по образцу `RegionResource`).
- Страницы: список, создание, редактирование.
- В карточке города — связанный справочник регионов (`RegionsRelationManager` переносится в `CityResource`); регион создаётся с `city_id` владельца.
- Действие «Открыть» у региона ведёт в существующую карточку региона (`RegionResource` edit) с улицами.
- Форма города: название, обязательное, уникальное внутри организации.
- Доступ — как у `RegionResource`: только оператор организации.

### RegionResource

- Карточка региона с улицами не меняется, кроме правила уникальности названия: уникальность внутри города вместо уникальности внутри организации.

### Карточка абонента

- Каскад из трёх полей: Город → Регион (только регионы выбранного города) → Улица (только улицы выбранного региона).
- Город у абонента не хранится: определяется через регион. Поле города в форме — фильтр, `dehydrated(false)`, при редактировании заполняется из `region->city_id`.
- Валидация: нельзя сохранить абонента с регионом чужого города или чужой организации; существующая валидация улицы по региону сохраняется.

## Что не меняется

- Зоны ответственности контроллёров: назначаются по регионам и улицам, город не участвует.
- Отчёты: группировка и фильтры по регионам без изменений.
- Печать квитанций: без изменений.
- Таблица абонентов: колонки без изменений.

## Тестирование

- Справочник городов: tenancy (город виден только своей организации), уникальность названия внутри организации, каскадное удаление регионов и улиц при удалении города.
- Регионы: уникальность названия внутри города; синхронизация `organization_id` из города.
- Карточка абонента: регион чужого города отклоняется; каскад фильтрует регионы по городу и улицы по региону.
- Миграция: существующие регионы привязываются к автоматически созданному городу «Город».
- Прогон тестов через `make test`.
